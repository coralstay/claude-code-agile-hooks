# 훅 시스템 구조적 문제 5가지와 컨텍스트 플래그 1차 구현

TASK-31의 설계/재현 기록. 사용자 지시는 "다섯 문제를 한 번에 풀려 하지 말고, 가벼운
'컨텍스트 플래그'부터 우선 대응한다(우선순위 높음)"였다. 이 문서는 (1) 다섯 문제와 각각의
재현 여부, (2) 컨텍스트 플래그의 확정된 형태와 스키마, (3) 1차 구현 범위와 남은 일을 적는다.

## 1. 다섯 문제와 재현 여부

| # | 문제 | 재현 여부 | 근거 |
| - | ---- | --------- | ---- |
| 1 | 턴어라운드 레이턴시 — 매 도구 호출마다 훅 프로세스를 새로 띄움 | 구조적으로 확인(계측 안 함) | Bash 한 번에 PreToolUse 훅이 최대 14개(`settings.hooks.json`), 각각 `python3` 기동 + 일부는 `backlog`/`git` 서브프로세스 실행 |
| 2 | 깨진 훅으로 인한 세션 마비 | **재현됨(2026-10-03)** | 아래 사건 A — 버그는 아니었지만 "훅이 필수 액션(Stop)을 반복적으로 막아 세션이 진행 불가"라는 증상은 동일 |
| 3 | 차단-재시도 무한 루프와 컨텍스트 왜곡 | **재현됨(2026-10-03)** | 사건 A — 같은 차단 메시지가 3회 연속 컨텍스트에 쌓임. Claude가 해소할 수 없는 조건(남의 dirty)으로 막았다 |
| 4 | 압축 시점의 데이터 유실 | 미재현 | `pre_compact_backup.py`가 transcript 원본은 백업하지만, 압축 후 세션 안의 훅/모델이 "압축이 있었다"는 사실을 알 방법이 없었다 |
| 5 | 병렬 처리 시 데이터 충돌 | **재현됨(여러 번)** | 사건 A, 그리고 이전 세션의 git-safety 훅 오탐, GitHub가 병합 시 재커밋해 생긴 로컬/원격 divergence |

### 사건 A (2026-10-03, 첫 재현 시나리오: 병렬 충돌 + 세션 마비)

1. 메인 세션이 같은 작업 트리를 수정하는 백그라운드 서브에이전트에 작업을 위임했다.
2. 서브에이전트가 아직 커밋하지 않은 변경을 갖고 있는 동안, 메인 세션이 턴을 끝내려 했다.
3. `block_stop_if_dirty.py`가 "커밋하지 않은 변경사항이 있습니다…"로 Stop을 **3회 연속**
   차단했다. 그 변경은 메인이 아니라 실행 중인 서브에이전트의 것이었다.
4. 메인은 커밋할 수도(남의 작업 중간 상태), 끝낼 수도 없어 트리가 깨끗해질 때까지
   busy-wait만 할 수 있었다.

원인: 훅은 "이 dirty가 누구 것인가"를 알 수 없었다. Claude Code가 Stop payload에 이미
넣어주는 `background_tasks` 필드를 무시해서 생긴 문제다.

## 2. 컨텍스트 플래그 — 확정된 형태

AC #2의 초안은 "훅 payload에 플래그를 추가한다"였지만, 훅은 Claude Code가 만드는 payload에
필드를 추가할 수 없다. 그래서 플래그는 두 가지 출처로 확정했다:

- **(a) Claude Code가 이미 보내지만 훅들이 무시하던 필드** — 해당 이벤트의 훅이 직접 읽는다.
  계측(Claude Code 2.1.267) 결과:
  - Stop: `background_tasks`, `stop_hook_active`, `last_assistant_message`, `permission_mode`,
    `prompt_id`, `session_crons`, `session_id`, `transcript_path`, `cwd`, `hook_event_name`
  - SessionStart: `source`(startup/resume/clear/compact), `session_id`, `transcript_path`, `cwd`
  - PreToolUse/UserPromptSubmit: `permission_mode` 포함
- **(b) 세션별 플래그 파일** — 한 이벤트에서만 보이는 사실(예: 압축이 일어났다)을 다른
  이벤트의 훅도 볼 수 있게 `context_flags.py`가 기록한다.

decision-3(라우터/dispatcher 없음, 완전 독립형)을 지키기 위해 플래그 파일은 공유 모듈이
아니라 **데이터 파일**이다. 쓰는 훅은 하나(`context_flags.py`)이고, 읽는 훅은 필요한 키만
직접 `json.load`한다. 파일이 없거나 깨졌으면 "모름"으로 취급해 기존 동작을 유지해야 한다.
두 훅이 같은 헬퍼(`background_tasks_running`)를 복붙하므로 `dedup_drift_guard.py`
REGISTRY에 등록했다(decision-2).

### 플래그 파일 스키마

경로: `$CC_HOOK_FLAGS_DIR/<session_id>.json` (기본 `~/.claude/hooks-logs/flags/`).
`session_id`는 basename만 사용(경로 탈출 방지). 쓰기는 임시 파일 + `os.replace`로 원자적.

| 키 | 타입 | 기록 시점 | 의미 |
| -- | ---- | --------- | ---- |
| `session_id` | str | 매번 | 세션 ID |
| `updated_at` | ISO-8601 UTC | 매번 | 마지막 기록 시각 |
| `last_start_source` | str | SessionStart | `startup`/`resume`/`clear`/`compact` |
| `post_compact` | bool | SessionStart | 압축 이후 상태. `compact`면 true, `startup`/`clear`면 false, `resume`이면 유지 |
| `compacted_at` | ISO-8601 UTC | SessionStart(compact) | 최근 압축 시각 |
| `compact_count` | int | SessionStart | 이 세션의 압축 횟수 |
| `compact_trigger` | str | PreCompact | `auto`/`manual` |
| `pre_compact_at` | ISO-8601 UTC | PreCompact | 최근 PreCompact 시각 |
| `parallel_session` | bool | Stop | `background_tasks`가 비어있지 않은 리스트/딕셔너리면 true |
| `background_task_count` | int | Stop | 그 개수 |
| `parallel_checked_at` | ISO-8601 UTC | Stop | 최근 Stop 시각 |

`retry_count`(AC #2 초안의 예시)는 넣지 않았다 — Stop 쪽은 `stop_hook_active`가 이미 같은
역할을 하고, PreToolUse 차단 재시도 횟수는 아직 소비자가 없다.

### 왜 `block_stop_if_dirty.py`는 플래그 파일이 아니라 payload를 읽는가

같은 이벤트에 걸린 훅들은 병렬로 실행되므로, 같은 Stop에서 `context_flags.py`가 쓴
`parallel_session`이 `block_stop_if_dirty.py`가 읽기 전에 반영된다는 보장이 없다. 같은
이벤트 안의 사실은 payload에서 직접 읽고, 플래그 파일은 **다른 이벤트**의 훅이 참고하는
용도로 쓴다.

## 3. 1차 구현 범위 (TASK-31)

- 새 훅 `hooks/context_flags.py` — SessionStart/PreCompact/Stop에 등록. fail-open(어떤
  예외든 exit 0). 테스트는 `CC_HOOK_FLAGS_DIR`을 tmp_path로 돌려 실제 `~/.claude`에 쓰지 않는다.
- `hooks/block_stop_if_dirty.py`가 플래그를 소비:
  - `background_tasks`가 비어있지 않으면(parallel_session) 통과 — 그 변경은 실행 중인
    백그라운드 작업 몫일 수 있다. 백그라운드 작업이 끝난 뒤의 Stop은 여전히 검사된다.
  - `stop_hook_active`는 통과 조건으로 쓰지 않는다. 커밋은 언제나 Claude가 할 수 있는
    일이라 반복 차단은 루프 버그가 아니라 강제력 자체다. 사건 A의 루프는 dirty의 주인이
    백그라운드 작업이었기 때문이고, 위 규칙이 그 경우를 덮는다.
  - 두 검사 모두 `backlog`/`git` 서브프로세스보다 먼저 해서, 해당 경우엔 레이턴시도 줄인다.
- `post_compact` 소비자는 아직 없다. 현재 transcript 내용에 의존하는 훅
  (`reserved_tag_guard.py`는 `last_assistant_message`만 읽고 transcript는 읽지 않음)이 없어서
  억지로 붙이지 않았다. 의도된 소비자:
  - 압축 직후 SessionStart에서 "현재 In Progress 태스크를 `backlog task view`로 다시 읽어라"를
    주입하는 훅(압축으로 task view 내용이 컨텍스트에서 사라졌을 수 있음)
  - `dead_end_registry.py`/`dead_rules_audit.py`처럼 세션 내 누적 통계를 쓰는 훅이 압축
    전후를 구분하는 용도

## 4. 남은 일

- 다른 차단 훅 중 Claude가 스스로 해소할 수 없는 조건으로 막는 곳이 있는지 점검(그런 곳만 `stop_hook_active`/재시도 상한 후보)
- 훅 단위 kill switch(예: 플래그 파일이나 환경변수로 특정 훅을 fail-open 강제) — 세션 마비 대응
- `post_compact` 소비자 구현(위 의도된 소비자)
- 병렬 서브에이전트가 같은 트리를 쓸 때의 근본 대응(워크트리 격리를 기본값으로 등)
- 레이턴시 실측(훅별 실행 시간 로깅)
- `background_tasks` 원소의 필드 구조(상태·종류 필드가 있는지)는 아직 덤프하지 않았다 —
  개수의 의미는 아래 5절에서 확인됨.
- 설치는 2026-10-03 사용자가 일괄 설치로 완료(추가 전용 병합, 다른 도구 훅 보존).

## 5. 실측: `background_tasks`는 실행 중인 작업만 담는다 (TASK-33, 2026-10-03)

설치된 `context_flags.py`가 Stop마다 남기는 `background_task_count`로 확인했다.

1. 90초 백그라운드 Bash 작업(A)을 띄운 채 턴 종료 → Stop 08:02:24, count = 1 (A 실행 중).
2. A 종료 알림으로 재호출된 턴에서, 30초 뒤 플래그 파일을 읽는 백그라운드 작업(B)을 띄우고
   턴 종료 → Stop 08:04:09, count = 1. 끝난 A가 남았다면 2였어야 한다.

결론: 끝난 작업은 목록에서 빠진다. `block_stop_if_dirty.py`의 "비어있지 않으면 통과" 판정은
작업이 끝난 뒤의 Stop에서 다시 검사로 돌아오므로, 서브에이전트를 한 번 띄운 세션에서 dirty
검사가 영구히 꺼지는 일은 없다. 상태 필터는 필요 없다.

한계: 백그라운드 Bash 작업으로 측정했다. 서브에이전트(Agent)도 같은 목록에 같은 방식으로
들어가는지는 다음에 백그라운드 서브에이전트를 띄울 때 같은 방식으로 count를 확인한다.
