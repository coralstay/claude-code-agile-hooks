> **2026-09-26: decision-10이 부분 대체.** "push·원격 병합은 사람이 최종 승인"은
> 유효하다. "로컬 fast-forward까지만 자동화" 문구만 대체됐다 — 병합은 머지 커밋으로 한다.
>
> **2026-10-03: decision-11로 다시 정리됨.** 로컬은 `main`에 rebase 후 fast-forward,
> 머지 커밋은 원격(GitHub PR) 병합에만 쓴다. 이 decision의 본문은 다시 유효하다.

## Context

README 0장/7장이 이미 "Phase 4.3 push 전 코드 리뷰"를 Phase 2(백로그 승인)와 함께 훅으로
대체 불가능한 필수 HIL로 규정하고 있다. 이번 세션에서 12개 태스크를 서브에이전트로
구현하면서, 각 태스크가 끝날 때마다 `git checkout main` 자체가 auto mode classifier에
막히는 걸 겪었다 — main 브랜치 전환/병합이 사람 승인이 필요한 액션으로 분류돼 있었다.

## Decision

서브에이전트에게는 매번 "git push나 main merge는 절대 하지 마라, 커밋까지만 하고
브랜치명/커밋 해시를 보고하라"고 명시적으로 지시했다. 코디네이터(나)가 각 태스크
완료 후 로컬에서 `git merge --ff-only`로만 브랜치를 통합했고, 원격 push/PR 머지는
사용자가 직접 승인하고 실행하도록 남겨뒀다(실제로 PR #5는 사용자가 GitHub에서 직접
머지).

## Consequences

- 모든 작업(TASK-1~12)이 로컬 main까지는 자동으로 진행됐지만, 원격에 반영되는 시점은
  전적으로 사용자 통제 하에 있었다 — 실수로 검증 안 된 코드가 원격에 올라갈 위험이
  없다.
- 대신 매 태스크마다 "다음 브랜치는 어디서 분기하는가"를 코디네이터가 직접 추적해야
  했다(main 병합이 막혀 있던 구간에는 브랜치를 스택으로 쌓아 순차 진행).
- 이 원칙은 앞으로도 유지된다 — 로컬 fast-forward 병합은 자동으로 하되, push/원격 병합
  앞에서는 항상 멈춘다.
