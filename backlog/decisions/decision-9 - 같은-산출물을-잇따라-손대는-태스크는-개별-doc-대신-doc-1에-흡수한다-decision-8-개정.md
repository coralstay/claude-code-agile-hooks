## Context

decision-8("태스크 완료 시 backlog doc를 개별로 만드는 걸 기본으로 한다")을 문자
그대로 따랐더니, TASK-13~21(README를 계속 손보는 9개 태스크) 중 9개 전부가 개별
doc(doc-3~11)로 쌓였다. 각 doc의 내용은 이미 두 곳에 더 있었다 — 해당 태스크의
`final_summary`, 그리고 `doc-1`(세션 회고)의 "TASK-N" 요약 문장. doc-N이 추가로
담은 건 사실상 "왜 이 방법을 택했나" 한 단락뿐이었는데, README 말투를 고치는 것
같은 단순 작업은 그 단락도 대부분 자명했다. 사용자가 "문서가 중복된다"고 지적하며
정리를 요청했다.

또한 이 과정에서 `backlog doc create -p <path>`의 서브폴더(`reference/`,
`retrospectives/`, `tasks/`)가 backlog.md가 정한 규칙이 아니라 코디네이터가 그때
그때 임의로 지은 이름이었다는 것도 드러났다 — 문서가 11개뿐인 상태에서는 폴더로
나눌 실익이 없었다.

## Decision

decision-8을 이 decision-9로 대체한다. 앞으로는:

1. 같은 산출물(예: README.md)을 잇따라 손대는 태스크는 개별 doc를 새로 만들지 않고,
   `doc-1`(세션 회고)의 "문제→해결→이유→결과" 표에 행을 추가하는 방식으로 흡수한다.
   태스크의 `final_summary`는 여전히 필수로 남긴다(backlog.md 공식 워크플로).
2. 개별 doc는 정말 독자적인 주제일 때만 만든다 — 예: `doc-2`(레퍼런스, README에 없는
   내용), 새 훅을 신설하는 것처럼 이후에도 단독으로 참조될 설계 문서.
3. `backlog/docs/` 밑에 서브폴더를 임의로 만들지 않는다 — 문서 개수가 실제로 많아져서
   탐색이 어려워질 때만, 그 시점에 필요성을 근거로 들어 사용자와 함께 정한다.

## Consequences

- `doc-1`이 계속 커지지만, 세션 하나의 회고 문서가 길어지는 것 자체는 문제가 아니다 —
  오히려 "어디를 봐야 전체 그림이 보이는지"가 한 곳으로 고정된다.
- `backlog doc`에는 삭제 명령이 없어서, 이번처럼 방침을 바꿔 기존 doc를 없앨 때는
  `git rm`으로 직접 지워야 한다 — CLI만으로 완결되지 않는 지점이라는 걸 인지하고
  진행한다.
- decision-8은 삭제하지 않고 그대로 둔다 — "그 시점엔 그렇게 판단했다"는 역사적
  기록이고, 이 decision-9가 그것을 대체한다는 사실 자체가 하나의 교훈이다.
